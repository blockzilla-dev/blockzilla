# Public archive cache measurement

All 73 public GETs passed without an API key. No provider RPC calls, body files, new Worker, proxy, block store, DNS change, route change, or production deployment were used. The test used Worker version `1cc2931c-a23d-464b-b8ee-00b0e49d978d` and slots 470555971, 470663944, 470771932, 470879999 through `archive.blockzilla.dev` at CDG. Existing canonical JSON and complete Wincode digests matched.

The 73 requests were 16 sequential profile reads, 8 normal fills, 48 measured hits, and one connection prime. All 16 profile reads returned BYPASS, positive origin reads, and zero reported archive cache hits. All 48 measured hits had zero origin reads, zero customer authentication KV reads, and zero customer billable reads. Binary profile reads used one owner R2 read plus two Foundation S3 range reads. JSON profile reads used two Foundation S3 reads. Normal fills are retained separately in the receipt.

“Cold” means that `profile=1` bypasses the Worker response, index, and range caches. It does not prove physically cold R2 caches or a new Worker isolate. Profile work adds CPU overhead. Body transfer time was recorded before digest and decode checks. One client connection was reused.

The current cache still runs the Worker. Cloudflare says a route invokes the Worker before the normal zone-cache lookup, and the Cache API is called inside the Worker. The controlled hit windows had positive platform CPU and estimated invocation counts. Both `CF-Cache-Status: HIT` and `X-Blockzilla-Cache: HIT` can appear on this path; neither header alone proves skipped execution. [Worker/cache order](https://developers.cloudflare.com/cache/interaction-cloudflare-products/workers/), [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/).

Platform counters estimated 22 binary and 19 JSON invocations for 24 HTTP hits in each window, from 10 and 16 raw samples. Their CPU estimates were 46,808 and 32,852 microseconds. These are adaptive estimates, not exact request accounting. Small-sample confidence flags are false. The exact HTTP 48-hit count and zero reported origin reads are separate measurements. Repeated metric queries were used only to allow analytics ingestion; they sent no extra data requests.

At the published marginal rates, the sampled warm CPU estimate gives about **$0.339 per million requests** for Worker requests plus CPU. This excludes included allowances, the base subscription, backend operations/storage, Foundation hosting, and bandwidth. It is not an invoice. Public customer billing headers do not describe Cloudflare fees. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/).

The minimal option to skip code execution is the documented **Workers Cache** on this same Worker: `cache: { enabled: true, cross_version_cache: false }`. It checks the cache first, supports streaming fills and tiered cache, and needs no new Worker or durable block copy. It is not enabled in the current version. Its outer hits still pay the standard **$0.30 per million** request rate beyond the allowance; they have zero Worker CPU charge. In this warm sample the possible CPU saving is about $0.039 per million. A zone Cache Rule alone does not put caching before a Worker route. [Workers Cache](https://developers.cloudflare.com/workers/cache/), [configuration](https://developers.cloudflare.com/workers/cache/configuration/).

Before activation, verify explicit no-store/private responses for errors, profiling, compact recovery, locator variants and authenticated routes. Keep version isolation. Check query keys and any required Vary headers. Test a producer-stream error before accepting cached streaming fills; the searched docs do not explicitly guarantee cache-commit behavior for that error. The documented cacheable response limit is 512 MB. The installed Wrangler schema supports this feature. No activation was attempted. [Cache keys](https://developers.cloudflare.com/workers/cache/cache-keys/), [limitations](https://developers.cloudflare.com/workers/cache/limitations/).

If zero Worker request fees on CDN hits are required, a possible design is normal zone cache → existing machine streaming origin → current Worker on a miss, with no local block store. It adds a miss hop and needs a separate bounded test and routing review. Serving the existing epoch R2 objects directly cannot generate the present per-slot JSON/Wincode endpoints. This is an architecture inference, not deployed behavior.

Evidence: `http.json`, `platform-cpu.json`, `summary.json`, `live-settings-before.json`, `live-settings-after.json`, `cache-proposal.json`, and `wrangler-schema-support.json`. Scripts in this directory reproduce the bounded test and metric query. No production file was edited.

Live follow-up: do not enable frontend Workers Cache for the current unknown-length JSON stream. An isolated 0% version enqueued a 64 KiB prefix and then called ReadableStream controller.error. A repeat returned cache HIT with the same producer UUID, origin ray and body hash. The test stopped and no production version was promoted. In a separate one-invocation comparison with frontend caching disabled, the existing Cache API rejected the errored put, returned no bad entry, passed the complete good-body digest control, and deleted both synthetic keys. The current Cache API architecture is retained. These tests read no real blocks and wrote no block body files. Full receipts are in ../cache-live-acceptance/RESULTS.md. The measured warm cost remains an estimate for the current Cache API path, not for the rejected frontend cache option.
